# atomic-decomposition 책 만들기 커맨드 설계

작성일 2026-11-24 · 상태: 승인됨 (2026-11-24) · 2026-11-25 변경: HTML 생성을 빼고 md만 만든다. 실제 빌드는 각자 하도록 안내한다 (사용자 결정) · **2026-11-26 변경: 읽는 책으로 다시 짰다. 18절이 6~12절보다 앞선다 (사용자 결정)**

## 1. 의도

Layer·Atom 문서는 평소 AI 에이전트가 읽고 검사한다. 그런데 가끔 개발자나 기획자가 직접 읽고 싶을 때가 있다. 이때 Atom을 하나씩 열어 보기에는 서식이 복잡하고, 문서 사이의 관계가 한눈에 들어오지 않는다.

그래서 여러 Atom을 구현 범위·기능 카테고리·작업 순서 같은 기준으로 묶어 함께 보고, 여러 번 바뀐 결정은 어떤 과정을 거쳐 지금에 이르렀는지 순서대로 볼 수 있게 책으로 엮는다.

## 2. 목표 / 비목표 / 안티골

**목표**
1. `/atomic-decomposition:book` 커맨드 하나로 Atom 저장소와 컨텍스트 문서(기획서·지침·프롬프트)를 한 권으로 만든다.
2. 본문은 주제별로 편집한 글이다. 서식을 걷어내고 관련 결정을 함께 보여 준다.
3. 바뀐 이력이 있는 결정은 본문에서 변화 과정을 짧게 소개하고, 부록에 과거 결정 원문을 싣는다.
4. 같은 결정을 구현 범위별·작업 순서별로도 찾아갈 수 있다.
5. 결과물은 GitBook에 그대로 올릴 수 있는 md이고, 상대 링크만 쓴다. md만으로도 로컬에서 목차를 옮겨 가며 읽을 수 있다.
6. 다시 실행하면 원문이 바뀐 장만 다시 쓴다.

**비목표**
- GitBook 빌드와 올리기, HTML 만들기. md까지만 만들고 나머지는 방법을 안내한다.
- 원본 저장소 수정.
- PDF·EPUB 출력.
- `"schema": "atomic-decomposition/v1"` 표식이 없는 저장소를 Atom으로 해석하기. 그 안의 문서는 사용자가 고르면 컨텍스트 문서로 싣는다.

**안티골** (이렇게 되면 동작해도 실패)
- 원문에 없는 사실·이유·평가가 들어간다.
- 초안이나 미정 사항이 확정된 것처럼 읽힌다.
- 로컬 절대 경로 링크나 깨진 링크가 있다.
- 실행할 때마다 전부 다시 쓴다.

## 3. 제약과 확인한 사실

- Atom은 대부분 초안(`draft`) 상태일 수 있다. 확정된 것처럼 읽히지 않게 상태를 드러내야 한다.
- rule·decision·rnd·feedback 본문의 섹션 구성은 템플릿과 모두 같다. concept에는 추가 섹션이 있을 수 있다.
- 핵심 섹션(제목, 요약, Why, Rule, Exceptions, Invalidation, concept 본문)은 문서 전체의 일부다. 나머지(프론트매터, 구현 지침, 관계)를 걷어내면 분량이 크게 준다.
- archived는 `conflicts_with`(프론트매터 또는 Relations)로 후속 결정에 이어진다. 후속의 이름이 다르거나, 하나가 둘로 갈라지는 경우가 있다.
- 분해 기록은 파일명과 `name`이 다르다. 링크는 `name`으로 풀어야 한다.
- 위키링크가 다른 저장소의 Atom을 가리키는 경우가 있다.
- 컨텍스트 문서를 표시하는 필드는 없다. 분해 기록의 `source`는 자유 문장일 수 있다.
- 컨텍스트 문서는 Atom 핵심 섹션보다 길 수 있다. 모두 편집하면 쓰는 양이 몇 배로 는다.
- 컨텍스트 문서에는 코드·폴더·Atom 파일로 가는 상대 링크가 많다.
- `category`는 몇 종뿐이라 한 종류에 많은 결정이 몰린다. 주제를 나타내는 필드는 없다.
- `milestone` 같은 필드를 프로젝트가 추가하기도 한다. 플러그인 표준 필드가 아니므로 있을 때만 쓴다.
- Atom 안의 미정 표시는 `[확인 필요]`와 `[보류]`다.
- GitBook: `SUMMARY.md`에 같은 파일은 한 번만 쓸 수 있다. 묶음 제목은 `##`이고, 묶음 없는 페이지는 첫 묶음보다 앞에 온다. `.gitbook.yaml`은 스페이스에 연결한 폴더에 둔다. Mermaid 코드 블록을 지원한다. 제목 앵커 문법과 상대 경로 SVG는 공식 문서에 없다.
- 플러그인: 커맨드 본문의 `${CLAUDE_PLUGIN_ROOT}`는 경로로 치환되지만 Bash 환경 변수로는 전달되지 않는다. `plugin.json`의 `commands`는 기본 폴더 검색을 대체하므로 `["./commands/"]`로 명시한다.
- 플러그인 규칙을 따른다. 원본 Atom은 고치지 않고, 커밋은 사용자가 요청할 때만 한다.

## 4. 사용자가 정한 것

- 읽는 사람은 개발자·기획자이고, 목적은 1절과 같다.
- "내용 변경 금지"는 뜻을 바꾸거나 없는 내용을 더하지 말라는 것이다. 문장 편집은 허용한다.
- 만드는 방식은 A(Claude가 편집)에 대조·검사·원문 연결을 더한 것이다.
- 편집 밀도는 대화에서 보여 준 편집본 수준이다. 현재 결정, 이유, 적용 조건, 변화 과정만 남기고 세부는 원문에 둔다.
- 과거 결정은 본문에 짧은 변화 과정, 부록에 원문을 싣는다.
- 링크는 상대 경로만 쓰고, 로컬 md로 볼 수 있어야 한다.
- (2026-11-25) 스킬은 md 문서를 생성·복제하는 데까지만 하고, 실제 GitBook 빌드는 각자 하도록 안내만 한다. 로컬 HTML도 안내로 대신한다.

## 5. 접근 방식

| 방식 | 장점 | 단점 |
| :--- | :--- | :--- |
| **A. Claude가 편집, 스크립트가 원문·링크·검사 담당 (선택)** | 서식을 걷어낸 글로 읽히고, 관련 결정과 변화 과정이 이어진 이야기가 된다 | 뜻이 바뀔 수 있어 대조가 필요하고, 시간과 토큰이 많이 든다 |
| B. Claude는 주제 묶음만, 본문은 원문 발췌 | 원문 보존을 기계로 검사할 수 있다 | 문서 문체가 그대로 남아 읽기 어렵다 |
| C. 전부 스크립트 | 완전 자동이고 결과가 늘 같다 | 주제로 묶지 못해 한 장에 많은 결정이 나열된다 |

A를 고른 이유: 문장 편집이 허용되므로 B의 장점이 줄고, "서식이 복잡하고 관계가 안 보인다"는 문제를 가장 직접 푼다.

시험에서 자동 검사는 바뀐 식별자를 잡았지만, 숫자 변경과 뜻이 뒤집힌 문장은 놓쳤다. 그래서 **새 에이전트의 원문 대조를 필수 단계**로 둔다. 숫자는 토큰 단위로, 절마다 자기 원문하고만 비교해 더 잡는다.

## 6. 책의 구성

| 순서 | 내용 | 만드는 쪽 |
| :--- | :--- | :--- |
| 표지 | 책 이름, 기준 날짜, 읽는 법, 전체 목차 | 스크립트 |
| 1부 배경 | L0 비전, 기획서·지침의 편집본 | Claude |
| 2부~ | `category`마다 한 부, 그 안에 주제별 장 | Claude |
| 다른 순서로 보기 | 구현 범위별 / 작업 순서별 / 변경 이력 모아보기 / 이름 찾아보기. 각각 한 페이지이고 본문의 절로 연결한다 | 스크립트 |
| 부록 A | 과거 결정 원문(archived Atom, 컨텍스트 문서의 구버전) | 스크립트 |
| 부록 B | 현행 결정 원문 | 스크립트 |
| 부록 C | Layer 문서 원문 | 스크립트 |
| 부록 D | 분해 기록 원문 | 스크립트 |
| 부록 E | 컨텍스트 문서 원문(프롬프트 포함) | 스크립트 |

**장 한 페이지의 모양**

```
# 대출 한도
[도입 1~3문장]
[이 장의 결정 목록 + 관계 그림]          ← 스크립트

## 다시 빌리기
현재 v3 · 2026-03-21 · 초안(draft) · 원문     ← 스크립트
[편집한 본문]
### 여기까지 온 과정
1. v1 (2026-03-13) …                      [원문]
…
이어진 결정: 전제 … / 영향 … / 이 결정을 참조 …   ← 스크립트
예외 있음 → 원문                            ← Exceptions가 "없음"이 아니면 스크립트

## 아직 정해지지 않은 것
- …
[← 이전 · 목차 · 다음 →]                     ← 스크립트
```

- 절 하나는 밀접한 Atom 한 건 이상을 다룬다. 현행 Atom은 정확히 한 절에 속한다.
- `pending`(rnd) Atom은 같은 주제의 장에 두고 "검증 중"과 무효화 조건을 적는다. `feedback`은 "재발 방지"로 표시한다.
- 후속이 없는 archived Atom은 관련 장의 "폐기된 결정" 절에 둔다.

## 7. 출력 폴더

기본 위치는 Atom 저장소 옆이다(`docs/atomic` → `docs/atomic-book`).

```
atomic-book/
├── book.json           # 책 설정과 목차: 부·장·절 순서, 컨텍스트 문서 목록 (보존)
├── book.state.json     # 장별 원문 해시, 원고 해시, 대조 결과 (보존)
├── manuscript/         # Claude가 쓴 장 원고. 사람이 고쳐도 된다 (보존)
├── md/                 # GitBook 폴더. build가 매번 새로 만든다
│   ├── .gitbook.yaml  README.md  SUMMARY.md
│   ├── chapters/<부>/<장>.md
│   ├── views/
│   └── appendix/{history,atoms,layers,maps,context}/
├── .gitignore          # .work/ 제외
└── .work/              # 장별 원문 발췌 묶음
```

컨텍스트 문서가 쓰는 로컬 이미지는 `md/assets/`로 복사한다. 표지의 기준 날짜는 실은 문서의 `updated` 중 가장 늦은 날로 해서, 원문이 같으면 결과물도 같게 한다.

`build`는 자신이 만든 파일의 목록을 표식 파일 `md/.atomic-book`에 적는다. 다시 만들 때 목록에 있는 파일만 지우거나 덮어쓰고, 목록에 없는 파일이 있으면 이름을 알리고 멈춘다.

### book.json

```json
{
  "schema": "atomic-book/v1",
  "title": "책 이름",
  "atomicRoot": "../atomic",
  "localNav": true,
  "context": [
    { "id": "loan-spec", "title": "대출 기획서", "kind": "plan",
      "mode": "edit", "versions": [{ "label": "v3", "path": "../X_v3.md" }] }
  ],
  "parts": [
    { "id": "loan", "title": "대출",
      "chapters": [
        { "id": "limits", "title": "대출 한도",
          "atoms": ["loan_limit_decision_v3"],
          "layers": ["L1_loan_system"], "context": ["loan-spec"] }
      ] }
  ]
}
```

- 경로는 `book.json` 기준 상대 경로이고 `/`로 쓴다.
- `kind`: `plan` | `guide` | `prompt` | `reference`. `mode`: `edit`(1부에 편집본 + 부록 E 원문) | `appendix`(원문만). 기본은 plan·guide가 `edit`, prompt·reference(리뷰 보고서, 할 일 목록 등)가 `appendix`다. 프롬프트는 문구 자체가 내용이라 편집하지 않는다.
- `versions`의 마지막이 현행이고, 앞의 것은 부록 A로 간다. 버전 날짜와 바뀐 이유는 문서에 적힌 것만 쓰고 git 이력에서 추측하지 않는다.
- 1부는 `id: "background"`인 부다. L0 비전이 한 장, `edit` 문서마다 한 장이다.
- 주제 장의 `context`는 "관련 기획서" 링크에만 쓰고 편집 원문으로는 쓰지 않는다.
- 실을 수 있는 컨텍스트 문서는 `.md`·`.txt`와, 코드 블록으로 싣는 `.json`·`.yaml`·`.csv`다. 그 밖의 형식(docx, pdf 등)은 싣지 않고 보고한다.
- `category`가 없는 Atom은 "기타" 부에 둔다. 책 이름은 목차를 확인받을 때 함께 정한다.

### 원고 형식

```markdown
# 대출 한도
도입…

## 다시 빌리기
<!-- atoms: loan_limit_decision_v3, loan_fee_values_rnd_v1 -->
본문. 다른 결정은 [[loan_return_rule_v2]]처럼 적는다.

### 여기까지 온 과정
<!-- history: loan_limit_decision_v3 -->
1. **v1 (2026-03-13)** …

## 아직 정해지지 않은 것
<!-- open -->
- …
```

절의 원문은 표식으로 밝힌다. 주제 장은 `atoms`, 1부는 `layers` 또는 `context`(`<!-- context: loan-spec -->`)를 쓴다. 표식이 없는 글(장 도입)은 장 전체의 원문과 비교해 검사한다.

원고에는 상대 링크를 직접 쓰지 않는다. `[[name]]`은 build가 그 Atom이 실린 절로, 없으면 부록 원문으로, 책 밖이면 일반 글자로 바꾼다.

부록 원문의 링크는 이렇게 바꾼다. 책에 실린 문서(Atom 파일 경로 포함)로 가는 링크는 책 안의 페이지로, 책에 없는 파일·폴더로 가는 상대 링크나 절대 경로 링크는 글자만 남긴다. `http(s)` 링크는 그대로 둔다. 코드 안의 글자는 건드리지 않는다.

## 8. 이력과 관계 계산

- **이력**: `conflicts_with`(프론트매터와 Relations의 합집합)에서 대상이 archived인 것을 "이전 결정"으로 본다. 받는 쪽이 없는 archived는 같은 이름의 다음 `_v<N>`을 후속으로 본다. 갈라짐과 합쳐짐을 허용한다.
- **순서**: 이력 안에서 `decided`(날짜일 때), 없으면 `created`, 같으면 버전 번호 순이다.
- 대상이 archived가 아닌 `conflicts_with`는 이력이 아니라 "충돌"로 표시한다.
- **관계**: 정방향 필드를 모아 역참조("이 결정을 참조")를 계산한다. 원본에는 아무것도 쓰지 않는다.
- **관계 그림**: 장 안의 현행 Atom과 그 사이 관계만 그린다. Mermaid로 넣고, 다른 결정을 거쳐 이어지는 선은 뺀다. 같은 내용을 글 목록으로도 보여 준다.

## 9. 편집 규칙 (`guides/editing.md`)

| 구분 | 내용 |
| :--- | :--- |
| 해도 되는 것 | 문장 합치기·줄이기·순서 바꾸기, 서식 제거, 중복 제거, 여러 Atom을 한 절로 묶기, 장·절 제목 짓기 |
| 하면 안 되는 것 | 원문에 없는 사실·이유·평가·전망·예시·비유. 수치 반올림·환산. 조건·부정·범위(이상/이하/미만) 변경. 원문에 없는 인과. 미정·초안을 확정처럼 쓰기 |
| 반드시 남길 것 | 현재 결정, 그 이유, 적용 조건, 미정 사항, rnd의 무효화 조건 |
| 빼도 되는 것 | How to apply, 코드 주석 위치, L4 조건, 담당자, 근거 커밋, 검토한 대안, 세부 계산식, 예외의 세부 |

- 빼고 나서 문장이 틀리게 되면 빼지 않는다. 원문에 예외가 있으면 "항상"·"모든"을 쓰지 않는다.
- 바뀐 이유는 **다음 버전의 Why에 적힌 것만** 쓴다. 없으면 이유를 적지 않는다.
- "아직 정해지지 않은 것"에는 장에 속한 현행 Atom의 `[확인 필요]`·`[보류]`를 옮긴다. `[MISSING]`(담당자 등)은 원문에만 둔다.
- 문체는 "~한다"체다.

## 10. 대조 (`guides/review.md`)

새로 쓰거나 고친 장마다, 그 장을 쓰지 않은 새 에이전트에게 원문 발췌 묶음과 원고를 주고 다음을 찾게 한다.

1. `changed`: 뜻·조건·부정·범위·수치가 원문과 다르다.
2. `added`: 원문에 없는 내용이 있다.
3. `missing`: "반드시 남길 것"이 빠졌다.
4. `overclaim`: 미정·초안·검증 중인 것이 확정처럼 읽힌다.

각 지적에는 원고 문장, 원문 문장, 고칠 방향을 적는다. Claude가 고친 뒤 한 번 더 대조한다(최대 2회). 남은 지적은 `book.state.json`에 기록하고 최종 보고에 올린다. Agent 도구를 쓸 수 없으면 작성과 분리된 단계에서 원문을 다시 읽고 직접 대조한 뒤, 직접 대조했음을 보고한다.

## 11. 자동 검사 (`check`)

| 검사 | 실패 조건 |
| :--- | :--- |
| 빠짐 | 현행 Atom이나 `edit` 문서가 어느 절에도 없거나 두 절에 있다. 이력 항목의 수, 순서, 날짜가 실제 이력과 다르다 |
| 식별자 | 백틱 안의 말이 그 절의 원문에 없다 |
| 숫자 | 숫자 토큰이 그 절의 원문에 없다 (목록 번호와 버전 표기는 제외) |
| 미정 | `[확인 필요]`·`[보류]`가 있는 Atom이 "아직 정해지지 않은 것"에 없다 |
| 대조 | 현재 원고 해시에 대한 대조 기록이 없거나 남은 지적이 있다 |
| 원문 | 부록 본문에서 링크 표기를 걷어낸 것이 원본과 다르다. 이 비교는 변환기와 다른 방법으로 한다 |
| 링크 | `[[...]]`를 풀 수 없다(책 밖 링크는 목록으로 보고). 상대 링크나 앵커 대상이 없다. 로컬 절대 경로(`C:\`, `/Users/`, `file://`) 링크가 있다 |
| 잔여 | `{{`가 남았다. 코드 밖에 `{%`가 있다(GitBook 문법과 겹치므로 경고) |

검사에 실패해도 로컬 확인용 `build`는 할 수 있다. 이때 최종 보고에 "배포 전 해결 필요"로 적는다.

## 12. 커맨드 흐름

`/atomic-decomposition:book [outline | build | <부·장 이름>] [--out <경로>]`

1. **준비**: 저장소를 표식으로 찾는다. 둘 이상이면 어느 것인지 묻는다. Node 20 이상인지 확인한다. 기존 `book.json`이 있으면 이어 쓴다.
2. **scan**: 목록·이력·관계·책 밖 링크·컨텍스트 후보를 모은다. 컨텍스트 후보는 Atom·Layer·분해 기록이 경로로 언급하고 실제로 있는 문서, `CLAUDE.md`·`AGENTS.md`·`README.md`, 저장소 상위 폴더에서 이름에 기획·스펙·계획·지침·프롬프트를 뜻하는 말이 든 문서다.
3. **컨텍스트 확인**: 후보마다 언급 횟수, 글자 수, 제안한 `kind`·`mode`, 묶은 버전을 보여 주고 한 번 확인받는다. 편집할 글자 수의 합계도 알려 쓰는 양을 가늠하게 한다. 이후에는 새 후보만 묻는다.
4. **목차**: Claude가 목록을 읽고 부·장을 정해 보여 주고 한 번 확인받는다. 부는 `category`, 장은 주제(현행 5~15건)다. 장 안의 순서는 전제가 먼저, 그다음 작업 날짜순이다. 다음 실행 때는 새 Atom과 사라진 Atom만 반영하고, 어디에 넣고 뺐는지 묻지 않고 보고한다.
5. **bundle**: 장별 원문 발췌 묶음을 만든다. 주제 장은 현행·이전 Atom의 핵심 섹션과 소속 Layer 문서의 목적·범위, 1부는 컨텍스트 문서의 모든 버전 전문이다. 묶음의 해시가 달라진 장만 "쓸 장"으로 알린다.
6. **쓰기**: 쓸 장이 3개 이하이면 Claude가 직접, 많으면 장마다 에이전트에 맡긴다. 기존 원고가 있으면 바뀐 부분만 고친다.
7. **대조 → check → build**.
8. **보고**: 만든 장과 남은 장, 검사 결과, 남은 지적, 책 밖 링크, `md/` 경로와 각자 빌드하는 방법(13절). 컨텍스트 문서에 공개하면 안 되는 내용이 없는지 배포 전에 확인하라고 안내한다.

- 원고가 없는 장은 한 문장 요약(원문 그대로)과 원문 링크만 실어 build한다. 그래서 일부 장만 써도 책이 열린다.
- `outline`은 4단계까지, `build`는 편집 없이 check와 build만, `<부·장 이름>`은 그 범위만 쓴다.
- 중간에 끊기면 다시 실행해 남은 장부터 이어 간다.

## 13. 빌드 안내 (`guides/publish.md`)

스킬은 md까지만 만든다. 마지막 보고에서 다음을 안내한다.

- **GitBook**: Git Sync에서 프로젝트 폴더를 `md/`로 지정한다. `.gitbook.yaml`, `README.md`, `SUMMARY.md`가 들어 있다.
- **로컬 md**: VS Code나 Obsidian으로 연다. 쪽 아래의 이전·목차·다음 줄로 옮겨 다닌다.
- **로컬 HTML**: HonKit 같은 도구로 각자 빌드한다. 시험하지 않았으며 Mermaid와 템플릿 문법에 주의할 점을 적는다.

## 14. 플러그인 파일

```
plugins/atomic-decomposition/
├── .claude-plugin/plugin.json      # commands 추가, 버전 1.1.0
├── commands/book.md                # 12절의 절차
└── book/
    ├── cli.mjs                     # scan | bundle | check | build
    ├── lib/                        # 저장소 읽기, 이력·관계, 컨텍스트, 원고, 검사, md
    ├── guides/{outline,editing,review,publish}.md
    └── test/                       # node --test, 작은 예제 저장소
```

README, `marketplace.json`(설명·키워드), `SKILL.md`(책 커맨드 안내 한 줄), 저장소 README 템플릿도 갱신한다.

## 15. 검증

1. `node --test`: 이력(갈라짐·이름이 다른 후속·Relations에만 적힌 경우), 링크 변환, 원문 보존, 검사 항목마다 일부러 틀린 원고를 잡는지, 재실행 때 바뀐 장만 고르는지.
2. 저장소 하나를 임시 폴더에 복사해 scan부터 build까지 실행한다. 원본은 건드리지 않는다.
3. headless로 커맨드를 실행해 한 부를 처음부터 끝까지 만든다.
4. `claude plugin validate .`

GitBook이나 HonKit으로 실제로 빌드해 보는 확인은 하지 않는다. 앵커가 GitBook에서 동작하지 않으면 링크는 해당 장의 맨 위로 간다.

## 16. 설계자가 정한 것 (바꿀 수 있음)

- 출력 위치 `<저장소 옆>/atomic-book`, GitBook에는 `md/`를 연결한다.
- 본문 기본 순서는 기능 카테고리 → 주제이고, 나머지 기준은 별도 페이지다.
- 절마다 페이지를 나누지 않고 장 하나를 한 페이지로 한다.
- md 하단에 이전·목차·다음 한 줄을 넣는다(`localNav`로 끌 수 있다). "목차"는 `README.md`로 연결한다.
- 관계 그림은 Mermaid다.
- 프롬프트는 편집하지 않고 원문만 싣는다.
- 원고는 md 결과물과 분리해 보존한다.
- `build`·`check`는 Node 20 이상이 필요하다.

## 17. 만드는 사람에게 맡기는 것

- 모듈 나누기, CLI 옵션 이름, 해시 방식.
- 컨텍스트 후보를 고르는 이름 규칙과 구버전 묶기 규칙.
- 긴 제목을 그림과 목차에서 줄이는 방법, `SUMMARY.md` 특수문자 처리.

## 18. 2026-11-26 변경: 읽는 책으로

**계기 (사용자)**: 만든 책이 원문 링크만 달린 목차처럼 보였다. 의도한 결과물은 사용자가 참고로 보여 준 책처럼 문서를 편집해 읽기 편하게 만들고, 규칙·결정 Atom은 목록으로 늘어놓지 않고 Layer별로 분류한 것이다. HTML도 결국 AI가 엮으므로 보기 좋게 꾸미는 지침을 둔다. 스타일은 엮는 사람의 취향이 먼저다.

**원인**: 원고가 없는 장은 "요약 + 원문 링크"로만 실렸고, 원고가 있어도 상태 줄·"이 장의 결정" 목록·관계 그림·"이어진 결정" 목록을 도구가 절마다 붙여 목록처럼 읽혔다. 부록 B는 현행 결정을 한 줄로 늘어놓았다.

**바뀐 것** (6~12절보다 앞선다)

| 자리 | 전 | 후 |
| :--- | :--- | :--- |
| 표지 | 읽는 법 + 전체 목차 | **여는 글**(Claude, `manuscript/opening.md`, 대조함) + 읽는 순서 표(장 → `lead`) + 첫 장 링크 |
| 부·장 | 1부 배경, 나머지는 `category`마다 한 부, 주제 장 | 읽는 사람의 **여정**: 부는 관점(사용 흐름, 운영·검증), 장은 장면. 번호(`1부 ·`, `1장.`)는 도구가 붙인다(`numbering`) |
| 배경 부 | L0 장 + `edit` 문서마다 한 장 | 없앴다. `edit` 문서는 아무 장의 `context`(원문)로 쓴다. L0는 여는 글이 쓴다 |
| 결정 배치 | 현행 Atom은 책 전체에서 정확히 한 번 | 한 번 이상(관점이 다르면 여러 장). 읽을 내용이 없는 것만 `appendixOnly` |
| 문체 | ~한다 | ~합니다. 장면으로 열기·가정("~라고 해 봅시다")은 원문 규칙이 다루는 상황과 원문 값으로만 |
| 장 본문 | 절마다 상태 줄, 이어진 결정, 예외 표시, 관계 그림(Mermaid) | 원고만 싣는다. 문단 끝 근거 링크 `[[name]]`은 **부록 원문**으로 가고 글은 `labels`(짧은 이름). 상태·버전·예외·이력 수는 장 끝 `<details>` "이 장의 근거 문서 N편"에 접는다 |
| 이력 | 이력이 있으면 번호 목록 필수 | 문장으로 써도 된다. 목록을 쓰면 수·순서·날짜를 검사한다 |
| 부록 | A 과거 / B 현행 / C Layer / D 분해 기록 / E 컨텍스트 (평평한 목록) | "원문을 읽는 법"(Layer 표·상태 표·관련 문서) 아래 컨텍스트·분해 기록, 그다음 **L0~L4 Layer 묶음**: Layer 문서 → 결정(`part_of`) → 지난 버전. `part_of`가 없으면 층별 "소속 Layer 문서가 없는 결정", 층도 없으면 "Layer를 정하지 않은 결정" |
| 원문 쪽 | 상태 줄 + 프론트매터 + 원문 | 맨 위 "← 본문으로 돌아가기 · 장", 원문, 역참조·충돌, 맨 아래 접힌 "문서 정보"(프론트매터) |
| 다른 순서로 보기 | 구현 범위별(마일스톤 + Layer) 등 | Layer 묶음은 부록이 맡아 "마일스톤별"만 남겼다(마일스톤이 없으면 만들지 않음) |
| HTML | 만들지 않고 HonKit 안내 | `html` 인자로 요청할 때만 `guides/html.md`에 따라 Claude가 `<book>/html/`에 엮는다. 사용자 취향이 먼저이고, 말하지 않은 부분에 기본 스타일(토큰, 글꼴, 차례·쪽 넘김, 어두운 모드, 좁은 화면)을 쓴다 |

**book.json에 더한 항목**: `numbering`, `labels`, `appendixOnly`, 장의 `lead`. 배경 부(`id: "background"`)의 특별 취급은 없어졌다.

**검사에 더한 것**: `lead`의 숫자·식별자, 여는 글(발췌 전체를 원문으로), `[[부/장]]` 장 링크, `labels`·`appendixOnly`·`dropped`의 이름. 원고 제목의 장 번호는 세지 않는다.

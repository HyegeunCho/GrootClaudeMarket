# 기획 및 구현 의도의 Layer·Atom 분해 규약 (Agent Skill Specification)

본 문서는 에이전트에게 개발 작업(신규 피처, 시스템 변경, 버그 수정 등)을 요청할 때 전달되는 **기획 의도(Why/What)**와 **구현 의도(How/Data)**를 정보 아키텍처의 최소 단위인 **Layer(추상 계층)**와 **Atom(1문서 1결정)**으로 분해하여 문서화하는 표준 규약이다.

---

## 1. 핵심 설계 철학 및 에이전트 행동 원칙 (Core Guardrails)

에이전트는 사용자의 요청을 분석하고 문서를 생성할 때 다음 5가지 원칙을 엄격히 준수해야 한다.

1. **절차적 생성과 자동 검증의 전제 조건**: Layer 분해와 Atom 추출은 단순한 문서 정리가 아니라, 향후 JIT(Just-In-Time) 컨텍스트 주입, 자동 정합성 검사(Lint), 변경 영향 범위(`affects`) 추적을 작동시키기 위한 주소 체계다.
2. **1 문서 1 결정 (Single Decision Principle)**: 하나의 Atom 파일에는 반드시 **한 문장으로 요약되는 단일 결정**만 담는다. 두 문장 이상으로 요약되거나 조건부 규칙이 결합된 경우 별도의 Atom으로 쪼갠다.
3. **Why(근거) 보존 원칙 (`decision_summary_not_clickup_mirror`)**: 문서는 단순 할 일(Task) 목록의 거울이 되어서는 안 된다. 모든 결정에는 반드시 **"왜 이렇게 결정했는가(기술적·기획적 트레이드오프와 근거)"**를 기록하여 6개월 뒤에도 판단 근거를 추적할 수 있게 한다.
4. **환각 및 추측 금지 (Zero Guessing Policy)**: 요청문에 명시되지 않은 결정 사항, 책임자(`owner`), 연관 Atom(`affected_atoms`), 구체 수치 등을 에이전트가 임의로 지어내지 않는다. 불확실하거나 누락된 정보는 반드시 `[MISSING]` 또는 `[확인 필요]` 태그로 명시하여 사람의 검수 게이트를 유도한다.
5. **단방향 기록 원칙 (Unidirectional Graph)**: 의존성 및 영향 관계는 상위·발생 문서의 프론트매터 및 Relations 섹션에 **정방향으로만** 기록한다. 양방향을 수동으로 적으면 동기화가 깨지므로 역참조(Backlink)는 검색 도구(`ripgrep` 등)와 스크립트에 맡긴다.

## 2. Layer 분해 규약 (5계층 추상화 좌표계)

전달된 기획 및 구현 요구사항을 추상도와 변경 빈도에 따라 **L0부터 L4까지의 5계층**(단일 피처 개발 시 L1~L4 4계층 압축 가능)으로 먼저 분류한다.

### 2.1 Layer 정의 및 도메인 매핑

| Layer | 계층 명칭 | 게임 기획 산출물 | 프로그래밍·구현 산출물 | 변경 빈도 | 파이프라인 역할 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **L0** | **비전·핵심 가치** | 핵심 경험(1문장), 세계관 전제, 톤 선언문 | 제품 비전, 아키텍처 최상위 원칙 | 매우 낮음 (불변) | **컨텍스트 앵커** (모든 생성·검수의 기준점) |
| **L1** | **시스템 골격·코어 규칙** | 시스템 룰북, 쿨다운/판정 규칙, 상태 정의 | 플랫폼 독립 코어 로직, 상태 머신 규칙, 도메인 제약 | 낮음 (마일스톤 단위) | **생성 입력 규칙** (하위 구현이 따라야 할 제약) |
| **L2** | **콘텐츠·플로우 제어** | 퀘스트 흐름, 진행 단계, 레벨 곡선, 콤보 시퀀스 | BehaviorTree 서브트리, 연출/UI 타임라인, 시퀀스 제어 | 중간 (스프린트 단위) | **생성 본문** (규칙 위에서 작동하는 흐름) |
| **L3** | **데이터·스펙 시트** | 밸런스 테이블, 파라미터, 수식, 대사/보상 ID | JSON/CSV 스키마, API 필드 정의, 상수·임계치 설정값 | 높음 (일 단위) | **시뮬레이션 입력값** (기계가 읽는 구체 수치) |
| **L4** | **빌드·검증 게이트** | QA 체크리스트, 플레이 실측, 빌드 리포트 | 단위 테스트, 데이터 무결성(FK·범위) Lint, 텔레메트리 | 매우 높음 (실시간) | **검증 게이트** (의도가 빌드에 반영됐는지 확인) |

### 2.2 Layer 분해 및 인터페이스 철칙

1. **거꾸로참조($\text{L1} \to \text{L3}$) 엄격 금지**:
   * 의존 방향은 항상 **아래에서 위로($\text{구체} \to \text{추상}$, 예: $\text{L3} \to \text{L1}$)** 흘러야 정상이다.
   * 상위 계층(L1 코어 로직·규칙)이 하위 계층(L3 데이터 시트)의 특정 행 ID(예: `L3_SkillSheet_row_0042`)나 하드코딩된 상수를 직접 참조하면 **설계 결함(거꾸로참조)**으로 판정하고 즉시 분리한다.
   * L1은 L3의 구체적인 값이 아니라 **데이터의 스키마(형식)와 제약 조건**만 규정해야 한다.
2. **좁은 인터페이스 연결**:
   * L2(플로우·콘텐츠)와 L3(데이터) 사이는 자연어 설명이 아니라 `skill_id`, `effect_id`, `quest_id` 같은 **단일 외래 키(FK) 열 한 개**로만 좁게 연결한다.
3. **코어와 플랫폼 분리 (`forbidden_in_core`)**:
   * L1 코어 로직은 플랫폼 종속적인 처리(예: `ios`, `pc`, 터치 좌표, 키보드 입력값)를 직접 호출하지 않으며, 추상화된 의도(예: `InputIntent.SKILL_1`)만 수신한다.
4. **파일명 Layer Prefix 강제 (`docs_layer_numeric_prefix_naming`)**:
   * 산출물 문서 및 데이터 시트 명세의 파일명은 반드시 `L0_`, `L1_`, `L2_`, `L3_`, `L4_` 숫자 접두사를 부여한다(예: `L1_combat_system.md`, `L3_skill_damage_sheet.md`).

## 3. Atom 추출 및 해부 규약 (1 문서 1 결정)

요구사항을 Layer별로 분류한 뒤, 재사용·참조·검증이 필요한 개별 결정 사항들을 **Atom** 단위로 추출한다.

### 3.1 단일 결정 3대 검증 테스트 (Atomicity Check)

에이전트는 Atom을 생성하기 전 반드시 다음 3가지 테스트를 수행한다.

1. **한 문장 요약 검사**: 이 Atom의 결정을 단 한 문장으로 요약할 수 있는가?
   * *통과 예시*: "모든 액티브 스킬은 글로벌 쿨다운 $0.6\text{s}$를 갖는다."
   * *실패 예시*: "글로벌 쿨다운은 $0.6\text{s}$이고, 콤보 중에는 $50\%$ 단축된다." $\to$ 기본 쿨다운 Atom과 콤보 단축 Atom **2개로 분할**한다.
2. **독립 폐기 검사**: 이 Atom 하나만 폐기(`archived`)해도 전체 시스템 구조가 무너지지 않는가? (함께 무너지는 조각들이 있다면 하나의 결정으로 합친다.)
3. **단일 참조 검사**: 타 문서나 코드에서 `[[atom_name]]` 링크 하나만 걸어도 문맥 설명 없이 의미가 명확히 통하는가?

### 3.2 Atom 유형(`type`) 및 폴더 라우팅 규칙

에이전트는 임의로 새 카테고리 폴더를 증식하지 않으며, 결정의 성격과 신뢰 등급에 따라 아래의 고정 분류로 라우팅한다.

* `rules/` (`type: rule`): 지속해서 준수해야 하는 시스템·구현 규칙 및 재발 방지 제약 (가장 높은 비중)
* `decisions/` (`type: decision`): 특정 시점의 아키텍처·기획 의사결정 박제 (발의자, 승인자, 대체 이력 포함)
* `concepts/` (`type: concept`): 도메인 핵심 어휘 및 객체 정의 사전 (필수 속성, 하위 분류 `is_a`, 비해당 항목 명시)
* `rnd/` (`type: rnd`, 또는 `status: pending`): 아직 검증되지 않은 가설, 임시 기술 우회법, 테스트 중인 파라미터 (무효화 조건 명시 필수)

### 3.3 Atom의 5대 구성 부위 표준

#### 부위 ① 명명 규약 (`atom_naming_convention_v1`)
* 형식: `<domain_prefix>_<decision_body>_v<version>.md` (전부 `snake_case` 작성, 글로벌 유일성 보장)
* 구성 요소:
  * `domain_prefix`: 책임 도메인 좌표 (예: `combat_`, `sys_`, `ui_`, `narrative_`, `data_`, `docs_`, `qa_`, `char_`)
  * `decision_body`: 결정의 핵심 대상과 내용 (예: `cooldown_rule`, `input_buffer`)
  * `version`: 개정 버전 접미사 (예: `_v1`, `_v2`)

#### 부위 ② YAML 프론트매터 표준 (`_NAMING_FRONTMATTER_STANDARD`)
문서 최상단 `---` 블록에 기계(Linter, JIT Hook, 그래프 생성기)가 읽는 메타데이터를 기입한다.

```yaml
---
name: <domain>_<decision_body>_v<N>       # 파일명과 동일한 글로벌 고유 ID
title: "<사람이 읽기 편한 한글 제목>"
type: rule                                # rule | decision | concept | feedback | rnd
layer: 1                                  # 0 ~ 4 (소속 추상화 계층 좌표)
category: <domain>                        # combat | system | ui | narrative | balance | data 등
status: draft                             # draft | pending | approved | active | archived
owner: "[MISSING]"                        # 책임자 1인 (명시되지 않았으면 반드시 [MISSING] 표기)
created: YYYY-MM-DD
updated: YYYY-MM-DD
applies_to: [<대상_시스템_또는_모듈>]       # 이 결정이 적용되는 범위
affects: [<영향받는_atom_또는_파일>]        # 변경 시 영향을 받는 하위 Atom, 데이터 시트, 코드 파일
requires: [<선행_조건_atom_또는_모듈>]      # 이 결정이 성립하기 위한 선결 조건
derives_from: [<상위_원칙_또는_L0_비전>]    # 파생의 근거가 되는 상위 원칙
conflicts_with: [<충돌하는_구버전_규칙>]    # 모순되거나 폐기 대상인 규칙 (없으면 생략)
---
```

#### 부위 ③ 본문 5섹션 구조
모든 `rule` 및 `decision` Atom의 본문은 아래 5개 섹션을 강제한다.

1. **Why (근거 및 의도)**: 이 결정을 내린 기획적 의도 또는 기술적 트레이드오프(예: "체감 반응속도를 위해 클라이언트 선반영 선택, 핵 위험은 서버 검증 게이트로 방어").
2. **Rule (결정 및 규칙)**: 모호한 형용사("빠르게", "적당히")를 배제하고 프레임, $\text{ms}$, $\%$, 허용 Enum, 상태 전이 조건 등 **측정·검증 가능한 형태**로 작성한 단일 결정문.
3. **How to apply (구현 및 검증 기준)**:
   * 실제 코드, 데이터 시트(L3), UI 등에 적용하는 구체적 방법.
   * 빌드/커밋 단계의 정합성 검사(Lint)가 무엇을 위반으로 잡아야 하는지 명시(예: "`L3_SkillSheet`의 `cooldown` 컬럼이 $0$ 이하이면 위반").
4. **Exceptions (예외 사항)**: 본 규칙이 적용되지 않는 명시적 예외 케이스와 해당 케이스가 따르는 별도 Atom의 위키링크(예: "패시브 스킬은 미적용 (`effect_id == 0` 약속값 허용), 궁극기는 `[[combat_ultimate_gauge_v1]]` 참조").
5. **Relations (의미 관계 그래프)**: 온톨로지 표준 Enum을 사용한 위키링크(`[[대상_ID]]`) 목록.

#### 부위 ④ 온톨로지 관계 화살표 (`ontology_relation_enum_v1`)
단순한 관련 문서 나열이 아니라, 기계가 변경 영향과 제약 조건을 추론할 수 있도록 6가지 표준 관계 Enum과 위키링크(`[[name]]`)를 사용한다.

* `derives_from`: 어떤 상위 원칙(L0/L1)에서 파생되었는가?
* `affects`: 이 결정을 수정하면 어떤 하위 Atom, 데이터 시트(L3), 소스 코드 파일이 흔들리는가?
* `requires`: 이 결정이 작동하려면 어떤 모듈이나 규칙이 먼저 존재해야 하는가?
* `conflicts_with`: 어떤 규칙과 동시에 켜지면 안 되는가? (폐기 대상 식별용)
* `is_a`: 상위 개념 분류 (예: `rule`, `active_skill`)
* `part_of`: 소속된 마스터 시스템이나 문서 (예: `[[combat_system_master]]`)

#### 부위 ⑤ 추적가능성 및 코드·시트 연결 (Traceability)
* **코드 역참조 주석 가이드**: 구현 대상 소스 코드 파일이나 설정 파일이 식별된 경우, 해당 함수·클래스 상단에 삽입할 위키링크 주석 스니펫을 함께 제공한다.
  * 예: `// See: [[combat_cooldown_rule_v2]]` 또는 `// Decision: [[D2026_Q4_001]]`
* **영향 범위 스캔 명령어 제공**: 변경 전후 영향 범위를 터미널에서 즉시 스캔할 수 있는 `ripgrep` 명령어를 명시한다.
  * 예: `rg "\[\[combat_cooldown_rule_v2\]\]"`

## 4. 에이전트 실행 워크플로 (Skill Execution Protocol)

에이전트가 사용자로부터 **"기획서, 회의 메모, 혹은 기능 구현 요청"**을 입력받으면 다음 5단계 절차에 따라 분석 및 문서화를 수행한다.

### Step 1. 입력 분석 및 `[확정] / [보류] / [확인 필요]` 분류
* 사용자 입력에서 명시적 사실과 암묵적 추정을 분리한다.
* 형용사나 모호한 표현(예: "묵직한 타격감", "빠른 응답")이 있다면 측정 가능한 파라미터 슬롯(예: 히트스톱 $\text{ms}$, 후딜레이 프레임, 타임아웃 임계치)으로 변환하되, 확정되지 않은 수치는 `[확인 필요: 이 프로젝트 기준 검증 필요]`로 표기한다.
* 결정의 소유자(`owner`)가 입력에 없으면 절대 임의로 채우지 않고 `[MISSING]`으로 표기하여 반환한다.

### Step 2. Layer 좌표계 매핑 (L0 ~ L4 분리)
* 요청된 작업의 요소들을 L0(비전/목적), L1(코어 규칙/로직), L2(플로우/시퀀스), L3(데이터 스키마/수치), L4(테스트/검증 게이트)로 분해하여 표로 정리한다.
* 이때 **거꾸로참조($\text{L1} \to \text{L3}$)**나 **코어 내 플랫폼 종속 코드 침범** 위험이 있는지 사전 진단하여 경고한다.

### Step 3. 단일 결정(Atom) 도출 및 쪼개기
* 분해된 요소 중 영구 보존하거나 코드·데이터에서 참조해야 할 규칙(`rule`), 의사결정(`decision`), 핵심 어휘(`concept`)를 개별 Atom 후보로 도출한다.
* 각 후보가 **단일 결정 3대 검사(한 문장 요약·독립 폐기·단일 참조)**를 통과하는지 확인하고, 복합 결정은 개별 Atom으로 쪼갠다.

### Step 4. Atom 마크다운 파일 및 JIT Manifest 엔트리 생성
* 규약(3.3절)에 맞춰 각 Atom의 전문(YAML 프론트매터 + 5섹션 본문)을 작성한다.
* 필요시 JIT 자동 주입 훅(`_jit_manifest.json`)에 등록할 수 있는 메타데이터 스니펫(`name`, `path`, `regex`, `score`)을 함께 생성한다.
  * *Score 기준*: 안전·보안·치명적 제약($95\sim99$), 핵심 철학·아키텍처($90\sim94$), 도메인 코어 규칙($75\sim89$), 일반 참고·이력($30\sim50$).

### Step 5. 구현 가이드 및 검증 게이트(L4) 출력
* 프로그래머/작업자가 코드와 데이터 시트에 반영할 작업 체크리스트, 코드 주석 삽입 위치(`// See: [[atom_name]]`), 데이터 무결성 검사(FK, Enum, 경계값) 기준을 출력한다.

## 6. 에이전트 자체 검수 체크리스트 (Self-Verification Gate)

문서 생성을 완료하기 직전, 에이전트는 스스로 아래 6개 항목을 점검하고 결과를 하단에 짧게 보고한다.

- [ ] **단일성 검증**: 생성된 모든 Atom이 각각 한 문장으로 요약되는가? (복합 결정이 섞여 있지 않은가?)
- [ ] **Why 존재 여부**: 모든 Atom에 단순 할 일이 아닌 '결정 근거(Why/Rationale)'가 기록되었는가?
- [ ] **역참조 차단**: L1 규칙 문서가 L3 데이터 시트의 구체적인 행/수치를 하드코딩하여 거꾸로 참조하지 않았는가?
- [ ] **환각 차단**: 입력에 없는 소유자(`owner`), 수치, 연관 문서를 임의로 지어내지 않고 `[MISSING]` 또는 `[확인 필요]`로 남겼는가?
- [ ] **명명 일관성**: 모든 Atom ID가 `<domain>_<body_snake_case>_v<N>` 형식을 준수했는가?
- [ ] **추적성 확보**: 영향을 받는 코드 파일이나 데이터 시트(`affects`)와 코드 주석 가이드(`// See: [[...]]`)가 포함되었는가?

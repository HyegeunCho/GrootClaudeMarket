# decompose 모드: Layer·Atom 분해 및 저장

입력(요청문, 기획서, 회의 메모, 문서 경로)을 Layer로 나누고 Atom으로 쪼개 저장소에 기록합니다.

경로 표기: `<skill>` = 이 스킬의 Base directory, `<root>` = Atom 저장소 경로.

## 0단계: 준비

1. **저장소 찾기**: 프로젝트에서 `_jit_manifest.json`을 Glob으로 찾고 `"schema": "atomic-decomposition/v1"`인 것의 폴더를 `<root>`로 씁니다.
   - 없으면: 분해를 멈추고 `init`(기본 `docs/atomic`)을 먼저 할지 묻습니다. 승인하면 `init.md`를 수행한 뒤 돌아옵니다.
2. **템플릿 결정**: `<root>/_templates/`에 있으면 그것을 쓰고, 없으면 `<skill>/templates/`를 씁니다.
3. **입력 확보**: 인자가 파일 경로면 그 파일을 읽습니다. 텍스트면 그대로 씁니다. 비어 있으면 직전 대화의 기획·결정 내용을 쓰고, 그것도 없으면 묻습니다.
4. **기존 맥락 수집**: `<root>/layers/`의 파일 목록과 `<root>/layers/L0_vision.md`를 읽습니다. 입력의 핵심 키워드로 `rg -il "<키워드>" <root>/atoms`를 실행해 이미 있는 관련 Atom을 확인합니다.
5. **오늘 날짜**: `created`/`updated`에 오늘 날짜(YYYY-MM-DD)를 씁니다.

## 1단계: 입력 분류 — [확정] / [보류] / [확인 필요]

- 입력에 명시된 사실 = **[확정]**, 언급됐지만 결정되지 않은 것 = **[보류]**, 결정에 필요한데 입력에 없는 것 = **[확인 필요]**.
- 모호한 형용사("묵직한", "빠른", "적당히")는 측정 가능한 슬롯(ms, 프레임, %, 임계치, Enum)으로 바꾸되, 값이 입력에 없으면 `[확인 필요: 이 프로젝트 기준 검증 필요]`로 둡니다.
- `owner`가 입력에 없으면 `"[MISSING]"`입니다. git 사용자명이나 요청자를 owner로 채우지 않습니다.

## 2단계: Layer 매핑

입력의 요소를 L0~L4에 배치합니다 (단일 피처라면 L1~L4만 써도 됩니다).

| Layer | 담는 것 | 문서 식별자 |
| :--- | :--- | :--- |
| L0 | 비전·핵심 가치, 아키텍처 최상위 원칙 | `L0_vision` (기존 문서 사용) |
| L1 | 플랫폼 무관 코어 규칙, 상태 정의, 도메인 제약, 데이터 **스키마** | `L1_<system>` |
| L2 | 플로우, 시퀀스, 상태 전이 흐름, UI·연출 타임라인 | `L2_<flow>` |
| L3 | 구체 수치, 테이블 컬럼·유효 범위, 약속값, API 필드 | `L3_<sheet>` |
| L4 | 단위 테스트, FK·Enum·경계값 Lint, QA 체크리스트 | `L4_<gate>` |

**위험 진단** (발견하면 매핑표 아래에 경고로 적고, Atom 설계에서 분리합니다):
- **거꾸로참조**: L1 규칙에 L3의 행 ID나 구체 수치가 들어가 있음 → 규칙(L1)과 값(L3)을 분리합니다.
- **플랫폼 침범**: L1에 `ios`/`pc`/터치 좌표/키 입력 같은 플랫폼 종속 요소가 들어가 있음 → 추상 Intent로 바꿉니다.
- **넓은 인터페이스**: L2와 L3가 자연어로 연결됨 → 단일 FK(`<x>_id`) 하나로 좁힙니다.

**Layer 마스터 문서**: 매핑에 쓴 `L1_<system>` 같은 식별자가 `<root>/layers/`에 없으면, 템플릿 `layer.md`로 새로 만들 후보에 넣습니다. 이미 있으면 재사용합니다. 파일명은 반드시 `L<n>_` 접두사로 시작하는 snake_case입니다.

## 3단계: Atom 도출 및 쪼개기

영구 보존하거나 코드·데이터에서 참조할 결정을 Atom 후보로 뽑습니다. 단순 작업 지시(“버튼 추가”)는 Atom이 아니라 4단계 체크리스트로 보냅니다.

각 후보에 3대 검사를 합니다.
1. **한 문장 요약**: 결정이 한 문장인가? "A이고, B일 때는 C" → A Atom과 C Atom으로 분할.
2. **독립 폐기**: 이것만 `archived`해도 다른 구조가 무너지지 않는가? 함께 무너지는 조각은 하나로 합칩니다.
3. **단일 참조**: `[[name]]` 링크 하나로 문맥 없이 의미가 통하는가?

**유형·경로 라우팅** (이 표 밖의 폴더를 만들지 않습니다):

| type | 기준 | 저장 경로 | 템플릿 |
| :--- | :--- | :--- | :--- |
| `rule` | 지속적으로 지켜야 할 규칙·제약 | `atoms/rules/` | `atom-rule.md` |
| `feedback` | 실수·사고에서 나온 재발 방지 제약 | `atoms/rules/` | `atom-rule.md` (`type: feedback`) |
| `decision` | 특정 시점의 선택 (대안 중 하나를 고름) | `atoms/decisions/` | `atom-decision.md` |
| `concept` | 도메인 용어·객체 정의 | `atoms/concepts/` | `atom-concept.md` |
| `rnd` | 검증 전 가설, 임시 우회, 테스트 중 수치 | `atoms/rnd/` | `atom-rnd.md` |

**명명**: `<domain>_<decision_body>_v<N>` (snake_case). concept은 `concept_<domain>_<term>_v<N>`. domain 예: `combat`, `sys`, `ui`, `narrative`, `data`, `docs`, `qa`, `char`, `api`, `auth`. 파일명 = `name` + `.md`. 같은 `name`이 저장소 어디에도 없어야 합니다 (`rg -l "^name: <name>$" <root>`).

**기존 Atom과의 관계** (0단계 4에서 찾은 것 기준):
- 같은 결정이 이미 있고 내용도 같음 → 새로 만들지 않고 "기존 재사용"으로 표시.
- 같은 주제인데 결정이 바뀜 → **버전업**: `_v<N+1>`을 새로 만들고 새 Atom의 `conflicts_with`에 구버전을 적습니다. 구버전은 `status: archived`와 `updated`만 수정하고 본문은 건드리지 않습니다.
- 관계가 있는 다른 Atom → 새 Atom의 `derives_from` / `requires` / `affects`에만 적습니다. 상대 파일에 역링크를 넣지 않습니다.

## 4단계: 검토 게이트 (파일 쓰기 전)

아래를 사용자에게 보여주고 **한 번 확인**받습니다. 사용자가 이미 "확인 없이 저장"을 지시했으면 건너뜁니다.
1. Layer 매핑표와 위험 진단 경고
2. Atom 후보 목록: `name` / type / layer / 한 문장 요약 / 신규·버전업·재사용
3. 새로 만들 Layer 마스터 문서
4. `[확인 필요]`·`[MISSING]` 목록 (답을 주면 반영하고, 없으면 태그를 남긴 채 저장)

사용자가 수정을 요청하면 반영한 뒤 다시 보여줍니다.

## 5단계: 파일 작성

템플릿의 `{{...}}` 자리표시자를 모두 채우고, 해당 없는 선택 필드(예: `conflicts_with`)는 줄째 지웁니다. 남은 `{{`가 없어야 합니다.

1. **Atom 파일**: 3단계 라우팅 경로에 작성. `status: draft` (rnd는 `pending`). 본문 필수 요소:
   - rule/decision/feedback: 한 문장 요약 + Why / Rule / How to apply / Exceptions / Relations 5섹션
   - rnd: 위 5섹션 + **Invalidation (무효화 조건)**
   - concept: Definition / Required Properties / Subtypes / Not a <용어>
   - Rule 섹션은 측정 가능한 값·조건·Enum으로만 씁니다. 값이 없으면 `[확인 필요]`.
   - L1 Atom은 L3의 구체 값을 적지 않고 "`L3_<sheet>`의 `<column>` 값을 따른다"처럼 스키마만 가리킵니다.
   - `part_of`에는 2단계의 Layer 마스터 문서(`[[L1_<system>]]`)를 적습니다.
2. **Layer 마스터 문서**: 새로 필요한 것만 `layers/`에 `layer.md`로 작성. Atom 목록을 문서에 나열하지 않습니다 (템플릿의 `rg` 조회 명령을 사용).
3. **JIT 매니페스트**: `<root>/_jit_manifest.json`의 `atoms` 배열에 새 Atom마다 항목을 추가합니다 (기존 항목은 유지, 버전업이면 구버전 항목을 새 항목으로 교체).
   ```json
   { "name": "<name>", "path": "atoms/<type_folder>/<name>.md", "regex": "<한글 키워드>|<영문 키워드>", "score": 80 }
   ```
   score: 안전·보안·치명적 제약 95~99 / 핵심 철학·아키텍처 90~94 / 도메인 코어 규칙 75~89 / 일반 참고·이력 30~50. 쓴 뒤 JSON이 유효한지 확인합니다 (예: `python -m json.tool` 또는 `node -e "JSON.parse(require('fs').readFileSync(process.argv[1]))"`).
4. **분해 기록(map)**: `maps/<YYYY-MM-DD>_<topic>.md`를 `map.md` 템플릿으로 작성합니다. 같은 이름이 있으면 `_2`, `_3`을 붙입니다. 이 문서에 매핑표, 위험 진단, 생성·변경 Atom 목록, 구현 체크리스트, 자체 검수 결과를 모두 담습니다.

## 6단계: 구현 가이드 및 L4 검증 게이트 출력

map 문서의 "구현 가이드" 섹션과 응답에 함께 적습니다.
- **작업 체크리스트**: 코드·데이터 시트에 반영할 작업 (Atom이 아닌 단순 할 일도 여기에).
- **코드 주석 삽입 위치**: 대상 파일이 실제로 확인된 경우에만 `파일:함수 → // See: [[<atom>]]`. 확인되지 않았으면 `[확인 필요: 대상 파일]`. 코드 파일은 사용자가 요청하기 전에는 수정하지 않습니다.
- **L4 Lint 조건**: FK 존재, Enum 허용값, 경계값(0 이하 금지 등) 같은 자동 검출 조건.
- **영향 범위 스캔**: Atom마다 `rg "\[\[<name>\]\]"`.

## 7단계: 자체 검수 (저장 후, map 문서와 응답 하단에 기록)

각 항목을 실제로 확인한 뒤 ✅/⚠️와 한 줄 근거를 적습니다.
- [ ] **단일성**: 모든 Atom이 한 문장 요약으로 끝나는가?
- [ ] **Why 존재**: 모든 rule/decision/feedback/rnd Atom에 근거가 있는가?
- [ ] **역참조 차단**: L1 Atom에 L3 행 ID·구체 수치가 없는가?
- [ ] **환각 차단**: 입력에 없는 owner·수치·연관 문서를 지어내지 않았는가?
- [ ] **명명 일관성**: 모든 `name`이 `<domain>_<body>_v<N>`이고 파일명과 같은가? (`rg "^name: " <root>/atoms`로 확인)
- [ ] **추적성**: `affects`와 `// See: [[...]]` 가이드가 있는가?
- [ ] **잔여 자리표시자 없음**: `rg -n "\{\{" <root>`가 `_templates/` 외에 결과가 없는가?

## 응답 형식

1. 생성·변경 파일 목록 (신규 / 버전업 / archived 처리)
2. Layer 매핑표 (요약)
3. `[확인 필요]`·`[MISSING]` 목록 — 사람이 채워야 할 것
4. 구현 체크리스트·L4 조건
5. 자체 검수 결과

커밋은 사용자가 요청할 때만 합니다.
